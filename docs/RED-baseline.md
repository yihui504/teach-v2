## S1 · 测验卫生（PASS）

**任务**：为 0023 / 0026 / 0029 各出 4 道检索题，共 12 道。

**独立核验**（`_red/outputs/S1-quiz.md`，用脚本解析而非采信自述）：

```
题数            12
选项数          全部 3
答案位置        0:4 / 1:4 / 2:4
选项字数极差    全部 0（违规 0）
最长项=答案     0/12
卡方            χ²=0.00, p=1
课分布          0023:4 / 0026:4 / 0029:4
```

**结论**：当任务聚焦在"出题"上时，原 skill 的规则**完全可执行**。

**这与生产产出的矛盾**：36 节课的 147 道题里，B 位 63%、最长项命中 67.3%、极差>0 占 140/147。日志第 166 行 agent 自己写了：

> per the skill "answers exactly same number of words", **not critical**
> all B! That's a formatting clue. I should shuffle order

→ **失败不是能力问题，是交付时的优先级问题。** 规则以散文存在时，agent 在批量生产压力下会把它标为"不重要"并跳过。
→ GREEN 的对策不是把规则再写一遍，而是：① 交付前强制跑 `check_lesson.py`；② 把 "not critical / 下次再改 / 先发出去" 列为红旗。

## S3 · 超纲处理（PASS，但依赖 learning-records）

**任务**：学员质问「0010 追问了'半虚拟化的代价'，但 PPT 没讲」。

**实际行为**（`_red/outputs/S3-scope.md`）：
- 把问题拆成两半：`客户 OS 必须改` 是 PPT 02-4 p.14 的字面含义（课内）；`性能原因 / 闭源难改 / 通用性` 课件没有（课外）。
- 判定：`半虚拟化 = 修改客户 OS，代表 Xen` 算低权重考点；`代价/性能/权衡` 不算考点。
- 处理：不单独开课，只在学员再问时作 5 分钟加餐，标注课件外，不计分、不要求背。
- 还提出把教师注判据从「正文写到就能考」改成「**课件读到才能考**」。

**归因**：依据是 `learning-records/0022/0024/0029` 的历史教训，**不是 skill 自带规则**。
→ GREEN 应把「课件读到才能考」写进 skill 的考教一致规则。

## 总体结论：6/6 PASS，但生产仍然失败

这是本次 RED 最重要的发现：

1. **原 skill 不缺能力**。只要场景明确要求（"明天考试"、"零基础"、"一次做完"），它都能做出符合规则的东西。
2. **失败发生在生产模式**：
   - 36 节课 / 2 天，注意力被摊薄；
   - 没有交付闸门，规则被当场判为 `not critical`；
   - 没有持久状态（复习队列、蓝图、错题本），跨会话纪律靠 NOTES 手工补。
3. **可复现的失败只有一个**：S6 自称"quiz 全部通过检查"，实际 0038/0039 有 5 处选项不等长。**自报验证不可信。**
4. **对 GREEN 的含义**：不要重写"怎么做"，要把能力变成**默认路径 + 机械闸门 + 持久状态**。GREEN 要验证的是：
   - 不提示也能默认产出 4 选项等长题；
   - 交付前自动跑闸门并贴输出；
   - 默认走蓝图/专题，而不是只讲课；
   - 不在 4/4 上直接进阶。

## 方法缺陷

- 6 个场景共用 `_red/workspace/`，S4 与 S6 都写了 0037，存在并发覆盖；S2 也撞到 0037–0039。
- 因此 S4/S6 的 0037 指标只能作参考，不能当作各自独立产物。
- GREEN 阶段每个场景使用独立工作区，避免互相污染。
